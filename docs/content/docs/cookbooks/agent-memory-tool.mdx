---
title: Memory as an agent tool
description: Hand Memsy's search to the model as a callable tool so a multi-step agent recalls on demand instead of prefetching every turn.
---

The other cookbooks **prefetch**: they call `search()` on every turn and paste the results into the system prompt. That is the right default for a chat UI, where nearly every turn benefits from context.

It is the wrong default for an agent. A ten-step agent run — read a file, call an API, do arithmetic, write a summary — needs the user's history on maybe one of those steps. Prefetching pays for ten searches and burns prompt tokens on nine irrelevant ones.

The alternative is to make recall a **tool** the model calls when it decides it needs it. The integration point here is not a framework; it is the agent loop itself, so this recipe is framework-free — it works the same in OpenAI's SDK, Anthropic's, or any loop you wrote yourself.

  <Step title="Declare the tool">
    The description is the whole interface. The model reads it and nothing else when deciding whether to call — a vague one produces an agent that either never recalls or recalls on every step, which is prefetching with extra latency.

    Note what the schema does **not** contain: there is no `actor_id` parameter. The model must not choose whose memories to read.

    <Warning>
    Never put `actor_id` in a tool schema. The model would then be choosing whose memories to read, from a value it can hallucinate or be talked into by the user. Bind the actor in your executor, from your session — as below.

  <Step title="Implement the executor">
    The executor closes over the actor id, so the model supplies only the query. It also returns a plain string: tool results go straight back into the model's context, and a raw JSON dump of scores and ids costs tokens the model cannot use.

    <Tabs>
      <Tab title="Python">
        ```python
        import os

        from memsy import MemsyClient
        from memsy.exceptions import MemsyError

        memsy = MemsyClient(
            base_url=os.environ["MEMSY_BASE_URL"],
            api_key=os.environ["MEMSY_API_KEY"],
        )


        def make_recall(actor_id: str):
            """Bind the actor once; the model only ever supplies `query`."""

            def recall(query: str) -> str:
                try:
                    # No threshold: the default 0.0 returns the top 5 on any
                    # tier. A floor cuts noise, but the useful value is
                    # tier-dependent — see /docs/searching-memory#threshold.
                    found = memsy.search(query, actor_id=actor_id, limit=5)
                except MemsyError:
                    # Tell the model the truth: the lookup failed, the user has
                    # no history. Otherwise it reports "you have never mentioned
                    # that" — a confident, wrong claim.
                    return "Memory lookup failed. Proceed without it."

                if not found.results:
                    return "No relevant memories found."
                return "\n".join(f"- {r.content}" for r in found.results)

            return recall
        ```
      </Tab>

        ```ts
        const memsy = new MemsyClient({

              // No threshold: the default 0.0 returns the top 5 on any tier.
              // A floor cuts noise, but the useful value is tier-dependent —
              // see /docs/searching-memory#threshold.
              const found = await memsy.search(query, { actorId, limit: 5 });
              if (found.results.length === 0) return "No relevant memories found.";
              return found.results.map((r) => `- ${r.content}`).join("\n");
            } catch {
              // Tell the model the truth: the lookup failed, not that the user
              // has no history. Otherwise it confidently claims the latter.
              return "Memory lookup failed. Proceed without it.";
            }
          };
        }
        ```

    <Tip>
    "No relevant memories found." and "Memory lookup failed." must be different strings. They mean opposite things to the model, and collapsing them into one turns an outage into the assistant telling users they never said something they did.

  <Step title="Run the agent loop">
    A tool-calling loop runs until the model stops asking for tools. The bound iteration count is not optional — a model that keeps re-searching will otherwise spin.

    <Tabs>
      <Tab title="Python">
        ```python
        import json

        from openai import OpenAI

        openai = OpenAI()

        MAX_STEPS = 6


        def run(actor_id: str, user_message: str) -> str:
            recall = make_recall(actor_id)
            messages = [
                {
                    "role": "system",
                    "content": (
                        "You are a personal assistant with access to the user's "
                        "long-term memory. Use the recall_memory tool when past "
                        "context would change your answer."
                    ),
                },
                {"role": "user", "content": user_message},
            ]

            for _ in range(MAX_STEPS):
                response = openai.chat.completions.create(
                    model="gpt-4o-mini", messages=messages, tools=[RECALL_TOOL]
                )
                message = response.choices[0].message
                messages.append(message)

                if not message.tool_calls:
                    return message.content or ""

                for call in message.tool_calls:
                    # `tool_calls` is a union of function and custom tool calls,
                    # and only the function variant carries `.function`. Every
                    # call still needs a reply: an assistant message whose tool
                    # calls go unanswered is rejected on the next request.
                    if call.type != "function":
                        messages.append(
                            {
                                "role": "tool",
                                "tool_call_id": call.id,
                                "content": "Unsupported tool call.",
                            }
                        )
                        continue

                    args = json.loads(call.function.arguments)
                    messages.append(
                        {
                            "role": "tool",
                            "tool_call_id": call.id,
                            "content": recall(args["query"]),
                        }
                    )

            # Out of steps. Returning a truthful failure beats returning the
            # model's last half-finished thought as if it were an answer.
            return "I could not finish that request."
        ```
      </Tab>

        ```ts
        import OpenAI from "openai";

        const openai = new OpenAI();
        const MAX_STEPS = 6;

        async function run(actorId: string, userMessage: string): Promise<string> {
          const recall = makeRecall(actorId);
          const messages: OpenAI.ChatCompletionMessageParam[] = [
            {
              role: "system",
              content:
                "You are a personal assistant with access to the user's " +
                "long-term memory. Use the recall_memory tool when past " +
                "context would change your answer.",
            },
            { role: "user", content: userMessage },
          ];

          for (let step = 0; step < MAX_STEPS; step++) {
            const response = await openai.chat.completions.create({
              model: "gpt-4o-mini",
              messages,
              tools: [RECALL_TOOL],
            });
            const message = response.choices[0].message;
            messages.push(message);

            if (!message.tool_calls?.length) return message.content ?? "";

            for (const call of message.tool_calls) {
              // `tool_calls` is a union of function and custom tool calls, and
              // only the function variant carries `.function` — TypeScript
              // rejects the access without this narrowing. Every call still
              // needs a reply: an assistant message whose tool calls go
              // unanswered is rejected on the next request.
              if (call.type !== "function") {
                messages.push({
                  role: "tool",
                  tool_call_id: call.id,
                  content: "Unsupported tool call.",
                });
                continue;
              }

              const { query } = JSON.parse(call.function.arguments) as { query: string };
              messages.push({
                role: "tool",
                tool_call_id: call.id,
                content: await recall(query),
              });
            }
          }

          // Out of steps — a truthful failure beats the model's last
          // half-finished thought presented as an answer.
          return "I could not finish that request.";
        }
        ```

  <Step title="Record the turn">
    Recall being on demand does not make recording optional — an agent that only reads never accumulates anything to read. `run()` deliberately knows nothing about sessions, so the write lives in a thin wrapper around it.

    <Tabs>
      <Tab title="Python">
        ```python
        def chat(actor_id: str, session_id: str, user_message: str) -> str:
            answer = run(actor_id, user_message)

            memsy.ingest(
                [
                    EventPayload(
                        actor_id=actor_id,
                        session_id=session_id,
                        kind="user_message",
                        content=user_message,
                    ),
                    EventPayload(
                        actor_id=actor_id,
                        session_id=session_id,
                        kind="assistant_message",
                        content=answer,
        ```

    <Tip>
    Ingest the user's message and the final answer — not the intermediate tool calls. The recalled memories are already in Memsy; writing them back as new events re-ingests your own output and, over enough turns, drowns the original facts in restatements of themselves.
    </Tip>

## Tool vs. prefetch

|  | Prefetch | Tool |
|---|---|---|
| Searches per run | One per turn | Zero to a few per run |
| Latency on turns that need memory | One search, in parallel with nothing | One extra model round trip, then the search |
| Latency on turns that don't | One wasted search | None |
| Prompt tokens | Memories in every prompt | Memories only when fetched |
| Failure mode | Irrelevant context distracts the model | Model doesn't call the tool when it should |

Neither dominates. Prefetch for a chat UI, tool for a multi-step agent — and note that "the model doesn't call it" is a real failure that shows up as an assistant plausibly claiming ignorance. Log tool-call rates; if recall is firing on under ~10% of turns in a memory-heavy product, the tool description is the thing to fix.

## What to watch for

- **`actor_id` in the tool schema.** The most dangerous version of this pattern. Bind it in the executor.
- **Returning JSON from the executor.** Scores and ids are tokens the model cannot act on. Return prose.
- **No iteration bound.** A loop with no `MAX_STEPS` can spin until your rate limit stops it.
- **Conflating "no results" with "lookup failed".** Different strings, always.
- **Re-ingesting recalled memories.** Record what the user said and what you answered, not what you looked up.

```ts
  type: "function" as const,
```
